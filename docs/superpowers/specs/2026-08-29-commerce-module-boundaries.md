# 商城与支付模块边界说明

## 目标

把现有「积分兑换」和后续「真实货币实体商城」拆成两条轨道，避免把页面、订单、支付、库存和退款揉成一层。

## 当前范围

- 保留现有积分兑换页作为虚拟道具轨道。
- 真实货币实体商城只做架构预留，不接入业务落单。
- 暂未实现的新功能统一用「开发中」弹窗提示，不做静默失败。
- 页面设计稿先行，再落接口与业务实现。

## 页面映射

- 首页：保留照护入口、百科入口和商城入口，不做合并。
- 百科：只承载知识内容，不承担交易、支付或订单状态。
- 积分兑换：虚拟权益主轨，独立于真实支付。
- 实物商城：商品展示、详情、订单确认、支付状态、订单详情与售后。
- 开发中弹窗：用于未落地功能，不让用户误以为已经可用。

## 责任边界

### App 层

- `app/points-shop.tsx` 只负责积分兑换、签到、积分明细入口。
- 新增 `app/shop/*` 只负责商城展示和下单意图，不负责最终金额计算。
- `app/(tabs)/wiki.tsx`、社区、个人页保持独立，不和商城共享业务状态。
- 新增真实商城页面时，App 只发起意图和展示结果，不计算最终金额、不决定是否扣库存、不判断支付是否成功。
- “开发中”弹窗属于前端可见状态，不代表业务已接通。

### 服务端业务层

- `server/routes/points.js` 只处理积分账本、签到、积分消费。
- 真实商城建议单独拆为 `orders`、`inventory`、`refunds`、`payments` 路由或同名域服务。
- 路由层只做参数校验和编排，核心规则放到域服务里。
- 订单创建、支付结果、售后状态都必须服务端落库，再同步给前端。

### 支付适配层

- 支付渠道必须独立成适配器，不直接散落在订单路由里。
- 适配器只负责渠道参数组装、回调验签、退款请求和结果映射。
- 服务端以自己的订单和支付流水为准，不以客户端返回值为准。
- 支付适配器与订单域、退款域解耦，避免后续换渠道时重写业务逻辑。

## 状态规则

### 1. 积分兑换轨

- 状态只需要：`created -> deducted -> delivered -> closed`。
- 兑换成功后直接发放虚拟权益，不走物流、不走支付回调。
- 同一笔兑换必须有唯一幂等键，重复提交只返回同一结果。

### 2. 真实商城轨

- 订单状态：`created -> pending_payment -> paid -> fulfilling -> shipped -> completed`。
- 异常状态：`cancelled`、`expired`、`refund_pending`、`refunded`。
- 支付状态：`init -> pending -> success | failed -> refunded`。
- 库存状态：`available -> reserved -> deducted -> released`。
- 页面状态至少要覆盖：商品详情、确认订单、支付中、支付成功、支付失败、订单详情、售后处理中。

### 3. 退款规则

- 只有已支付订单才能退款。
- 发货前优先整单退款并释放库存。
- 发货后进入售后流程，退款单与原支付单强绑定。
- 退款、回调、重复点击都必须幂等。

## 信任边界

- 客户端只能传递商品选择、收货信息、意图与幂等键。
- 价格、优惠、运费、库存、退款金额都由服务端计算。
- 客户端本地状态只能用于展示，不能作为下单或支付成功的最终依据。
- 支付回调必须验签，且只接受服务端可验证的订单号、支付单号和金额。

## 执行顺序

1. 先完成 Figma 设计稿，明确页面与状态展示。
2. 再落模块边界与接口契约，先保住积分轨，再补真实商城域。
3. 先做订单、库存、支付适配器骨架，再接真实支付渠道。
4. 最后补退款、售后和发货流转。
5. 所有未接入能力统一显式提示「开发中」。

## 关键决定

- 积分兑换和真实支付分轨，不能共用同一套状态机。
- 支付能力必须做适配层，避免渠道代码污染订单域。
- 客户端不可信，所有金额和状态推进以服务端为准。
- 暂未实现的模块先用「开发中」提示，避免误导用户。
- 商城可以先展示完整交易链路，但下单按钮在接通支付前保持禁用。
