# 通知事件真实生成设计

## 目标

让社区互动真正闭环：用户 B 对用户 A 的内容发表评论、回复、点赞或关注后，A 可以在通知中心看到一条真实通知，并通过现有接口标记已读。

## 范围

本轮只接入三类业务事件：

- 帖子点赞：`type = like`，目标为帖子。
- 帖子评论和评论回复：顶级评论使用 `type = comment`，回复使用 `type = reply`，目标为帖子或评论。
- 关注用户：`type = follow`，目标为用户。

明确不包含：收藏通知、私信通知、系统公告、邮件推送、WebSocket 实时推送和通知设置扩展。

## 行为规则

1. 事件发起者与接收者相同则不写通知，避免自赞、自评、自我关注产生噪音。
2. 点赞和关注只有“新增关系”时写通知；取消点赞、取消关注不写通知。
3. 每次新增评论都写一条通知。顶级评论通知帖子作者；回复优先通知被回复用户，缺少有效被回复用户时通知帖子作者。两类通知都以原帖子为跳转目标，避免通知页将评论 ID 误作为帖子 ID。
4. 已有通知不做全局去重；同一用户重复产生真实互动时允许多条记录，避免丢失行为事实。
5. 事件写入必须和对应业务变更处于同一个数据库事务中。通知写入失败时，点赞、评论或关注也必须回滚，不能出现业务状态与通知状态不一致。

## 服务端设计

新增 `server/utils/notifications.js`，提供事务内 helper：

`createNotification(connection, { userId, fromUserId, type, targetType, targetId, content })`

helper 只负责参数化插入，不自行提交事务，不吞掉数据库异常。各业务路由在已经持有的事务连接上调用它：

- `server/routes/posts.js` 的新增帖子点赞分支：先锁定帖子作者，写点赞、更新统计、写通知，再提交。
- `server/routes/comments.js` 的评论创建事务：锁定帖子作者；回复场景额外读取父评论的作者或请求中的目标用户，写对应通知，再提交。
- `server/routes/users.js` 的新增关注分支：写关注关系、更新计数、写通知，再提交。

现有取消分支保持无通知行为。收藏路由保持不变。

## 客户端行为

通知列表继续使用现有 `/api/notifications`，不增加 mock fallback。通知点击规则沿用当前页面：帖子/评论通知进入帖子详情，关注通知进入用户主页；通知读取失败显示现有错误和重试状态。

## 验收与测试

服务端冒烟新增断言：

- B 评论 A 的帖子，A 未读数增加并返回 `comment` 通知。
- B 回复 A 的评论，目标用户收到 `reply` 通知。
- B 点赞 A 的帖子，A 收到 `like` 通知；取消点赞不新增。
- B 关注 A，A 收到 `follow` 通知；取消关注不新增。
- A 自己点赞、评论和关注自己的边界行为不产生通知（关注自身接口本身应保持 400）。
- 通知的标记已读和全部已读后，未读数正确下降。

UI 冒烟只验证真实通知在通知中心可见，并可进入目标帖子；不在本轮扩大视觉改版。

## 风险与后续

当前通知表没有唯一去重键，允许同一互动产生多条历史通知。若后续需要合并通知，应单独设计聚合窗口和幂等键，不在本轮临时修改表结构。
