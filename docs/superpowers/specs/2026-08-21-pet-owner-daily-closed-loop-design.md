# 已养宠用户日常闭环设计

日期：2026-08-21
阶段：多用户社区 MVP 的第一实施阶段

## 1. 目标与完成定义

本阶段将现有项目从“页面可演示、部分模块使用本地降级数据”收敛为“两个真实用户可在同一 MySQL 数据库中完成日常养宠社区闭环”。

目标路径：

```text
游客浏览百科/社区 -> 注册或登录 -> 创建主宠档案 -> 发帖 -> 另一用户评论/收藏
-> 签到获得积分 -> 在个人中心查看主宠、积分、帖子与收藏
```

完成时，线上业务事实仅保存在服务端 MySQL；前端不得在 API 失败时伪造注册、帖子、积分或主宠档案成功结果。

## 2. 产品约束

- 目标用户：已养宠用户。
- 形态：多用户社区，不是单用户本地演示。
- 游客权限：可浏览百科、社区帖子列表、帖子详情和评论。
- 登录权限：可创建/编辑自己的主宠档案、发帖、评论、点赞、收藏、签到，并查看个人中心私有结果。
- 主宠范围：每个用户仅有一只主宠；字段为品种、昵称、生日、性别、头像。
- 不在本阶段：虚拟宠物养成、答题排行榜、真实商城、私信、AI 档案上下文、内容审核后台、多宠管理、病历和健康档案。

## 3. 模块边界

### 3.1 认证与会话

职责：注册、密码登录、Token 刷新、登出和应用启动时会话恢复。

契约：

- 认证失败必须向前端返回可展示的错误；不得降级为 Mock 登录。
- 访问令牌只由认证 API 签发；刷新令牌由现有安全存储工具管理。
- 身份状态只由 `AuthContext` 持有；其他模块通过它读取当前用户和权限。

### 3.2 百科浏览

职责：游客/登录用户均可浏览品种列表、筛选、搜索和品种详情。

契约：

- `breeds` 表为唯一品种事实源。
- API 无法访问、返回错误和返回空列表是三种独立状态，UI 必须明确展示，不能以本地静态数据冒充服务端数据。
- 选择某个品种可作为创建主宠档案的预填输入。

### 3.3 社区内容与互动

职责：帖子浏览、详情、发帖、评论、点赞、收藏、个人帖子和收藏。

契约：

- `posts`、`comments`、`likes`、`bookmarks` 为唯一事实源。
- GET 帖子/详情/评论路由继续使用可选认证，以计算已登录用户的互动状态；游客不能写入。
- 发帖、评论、收藏失败时必须回滚乐观 UI 或重新请求服务端状态。
- `postService` 的 Mock 帖子只能删除或隔离到显式开发工具中；生产/正常开发主链路 API 失败时显示错误或重试状态。

### 3.4 签到与积分

职责：今日签到状态、每日签到、积分摘要、积分流水，及由服务端业务事件触发的奖励。

契约：

- `check_ins`、`points_history` 和 `users.points` 为积分唯一事实源。
- 签到、发帖、评论奖励在服务器内发放；客户端不能提交任意积分数额。
- 禁止普通客户端使用 `POST /api/points/earn`；该路由必须移除，或改为不可由用户凭 Token 直接调用的内部服务能力。
- `pointsService` 删除本地积分/本地签到降级；失败时返回错误状态。
- 用户每天只能签到一次，数据库唯一键是最终约束。

### 3.5 主宠档案

职责：创建、读取、更新和替换一只真实主宠档案。

不复用 `virtual_pets`：该表包含虚拟养成的状态、成长和互动时间，不符合真实宠物档案的业务语义。

新增表：

```text
user_pets
- id VARCHAR(36) primary key
- user_id VARCHAR(36) not null unique
- breed_id VARCHAR(50) not null
- name VARCHAR(50) not null
- birthday DATE null
- sex ENUM('male', 'female', 'unknown') not null default 'unknown'
- avatar_url VARCHAR(500) null
- is_primary BOOLEAN not null default true
- created_at TIMESTAMP default current_timestamp
- updated_at TIMESTAMP default current_timestamp on update current_timestamp
```

约束：

- `user_id` 唯一，实现一用户一主宠。
- `breed_id` 外键指向 `breeds.id`。
- 仅档案所属用户可读写；默认不在其他用户公开资料中暴露。
- 创建/更新操作均验证品种存在、昵称非空且长度不超过 50。

后端接口：

```text
GET    /api/user-pets/me
POST   /api/user-pets/me
PUT    /api/user-pets/me
DELETE /api/user-pets/me
```

所有接口均要求认证。`GET` 在未创建档案时返回 `data: null`，不是 404。

### 3.6 个人中心聚合

职责：展示当前用户的头像昵称、主宠、当前积分、今日签到状态、帖子数量、最近帖子和收藏入口。

契约：

- 个人中心不拥有业务数据，也不计算积分。
- 主宠来自 `GET /api/user-pets/me`；积分来自 `/api/points/summary`；收藏来自 `/api/bookmarks`；帖子来自 `/api/users/:id/posts`。
- 每个子请求失败都显示局部错误/重试，不能用静态数字替代。
- 登出后清空私有页面状态，游客态只显示登录入口和公开浏览导航。

## 4. 数据流与权限

```text
游客 -> GET /api/breeds, /api/posts, /api/posts/:id, /api/posts/:id/comments
登录用户 -> AuthContext -> Bearer Token -> 写入 API
写入 API -> MySQL transaction / 业务规则 -> JSON response
前端 -> 用 response 刷新或校正局部 UI -> 个人中心聚合真实结果
```

主宠、积分、收藏和帖子均按 `req.user.id` 隔离。请求体中不得接受可替代当前用户身份的 `userId`。

## 5. 现有实现的必改项

1. 移除 `src/services/authApi.ts` 中面向正常应用流程的 Mock 用户分支。
2. 移除 `src/services/postService.ts` 在 API 失败或第一页为空时返回 Mock 帖子的分支。
3. 移除 `src/services/pointsService.ts` 的本地签到、积分、消费降级。
4. 将前端当前的 `PetContext`/`petService` 虚拟宠物状态与新增真实主宠档案服务分离，不把主宠档案接入虚拟宠物衰减和经验逻辑。
5. 禁止客户端任意调用 `/api/points/earn`；保留服务端 `awardPoints` 供帖子与评论等受控业务事件复用。
6. 处理所有受影响页面的加载、空、未登录和错误状态，避免 API 失败时视觉上显示业务成功。

## 6. 数据库迁移与一致性

- 新建连续编号迁移 `006_user_pets.sql`，只创建 `user_pets` 及必要索引和外键。
- 同步更新 `server/full_schema.sql` 和 `scripts/db-summary.js`，使新库与迁移库都能验证 `user_pets`。
- 迁移不得修改、删除或重置 `virtual_pets`、`users`、`posts` 或现有业务数据。
- 需要为旧用户补档案的提示，但不自动生成虚假主宠。

## 7. 实施顺序

1. 建立 `user_pets` schema、迁移、路由和服务端测试。
2. 新增前端真实主宠服务与档案编辑入口，个人中心改为读取真实主宠。
3. 收紧认证、帖子列表和积分的 Mock/降级逻辑，补全错误状态。
4. 移除客户端积分直加入口，保证发帖/评论/签到的服务端积分流水正确。
5. 将个人中心接到主宠、积分、帖子、收藏的真实聚合数据。
6. 使用两个新测试用户跑完整闭环：A 发帖，B 评论/收藏，A 签到并在个人中心查看结果。

## 8. 验收标准

### 8.1 游客

- 可以浏览百科、社区帖子、帖子详情及评论。
- 访问任何写操作时被引导登录，且数据库不产生写入。

### 8.2 用户 A

- 注册后创建主宠并在刷新后仍能看到。
- 发帖后帖子在社区和个人中心均可见，且获得一次受控发帖积分。
- 完成今日签到后，余额、连续天数和积分流水一致。

### 8.3 用户 B

- 注册/登录后可看到 A 的帖子。
- 评论和收藏 A 的帖子，A 的数据不被 B 的私有收藏混入。
- B 的积分、签到和主宠数据与 A 隔离。

### 8.4 系统行为

- API 不可用时，认证、帖子、积分、主宠模块都显示失败状态，不返回本地伪成功数据。
- 后端 smoke 覆盖用户 A/B 的帖子、评论、收藏、签到、主宠和积分断言。
- UI smoke 覆盖游客浏览、登录拦截、创建主宠、发帖、评论、收藏、签到和个人中心展示。

## 9. 非目标与后续扩展

- `virtual_pets` 保持现状并作为后续独立“云养宠”模块；不得用于真实档案。
- 多宠、宠物公开主页、品种内容推荐、AI 自动带入主宠信息均在本阶段完成后单独设计。
- 内容审核、举报处理后台、对象存储和生产发布依旧是独立安全/运维阶段。

## 10. 邮件能力延期决策（2026-08-22）

本阶段暂不配置邮件服务商、SMTP、域名 DNS 或服务器发信能力。先完成并验证不依赖外部邮件服务的功能需求，待本地功能检查完毕、准备部署服务器时统一接入。

### 当前已纳入验收范围

- 注册时填写并保存邮箱。
- 使用邮箱和密码登录。
- 使用用户名和密码登录保持兼容。
- 邮箱格式校验与邮箱唯一性约束。
- 邮箱密码重置接口保留现有开发态 `debugToken` 流程，仅用于本地测试。

### 当前明确不纳入验收范围

- 注册激活邮件。
- 邮箱真实性验证和 `email_verified_at` 状态限制。
- 邮箱验证码登录。
- 生产环境邮件模板、退信处理和邮件发送重试。

### 后续服务器配置前置条件

1. 确定邮件服务商并取得 SMTP/API 凭据。
2. 配置服务器环境变量、正式站点 URL 和发件人地址。
3. 配置发信域名的 SPF、DKIM、DMARC。
4. 新增邮箱验证 Token、邮箱登录验证码的数据表及限流策略。
5. 接入激活邮件、验证码邮件和密码重置邮件发送服务。
6. 在生产配置完成后重新执行注册、激活、密码登录、验证码登录和密码重置回归测试。

在上述配置完成前，不得把开发态 `debugToken` 当作生产邮件能力，也不得在前端伪造“邮件已发送”或“邮箱已验证”的成功状态。
